# Fragile areas — After Effects and ExtendScript

Measured behaviour of After Effects 2026 and its scripting engine, and the
decisions in `packages/jsx/` that follow from it. Everything here was found by
running against a live AE; several entries contradict Adobe's documentation.
**Undo behaviour, frame rendering and the TextDocument round trip are measured
before they are claimed anywhere.**

## ExtendScript, the language and `run_jsx`

- ExtendScript single-threading: `run_jsx` with a long synchronous loop will freeze AE's UI. Document for the agent in the tool description (already done).
- **ExtendScript parses chained ternaries left-associatively.** `a ? x : b ? y : z` evaluates as `((a ? x : b) ? y : z)`, so the first truthy branch becomes the next condition and everything falls through to the last alternative — no throw, just the wrong answer. `get_project_summary` labelled every project item `"folder"` for two releases on one such line (issues #21/#22). Write if/else chains in `packages/jsx/*.jsx`; parentheses parse correctly too, but a later edit can drop them. `tests/unit/jsx-ternary.mjs` scans the sources and fails the build — there is no offline ExtendScript runtime, so nothing else can.
- **`run_jsx` must never answer `null`.** A script whose last statement is a bare expression completes and yields `undefined` — `"ping";` does not return `"ping"` — with every side effect already applied. Answering that with a bare `null` made "ran fine, returned nothing" identical on the wire to "did not run", and the natural response to a suspected failure is to run the script again: nothing rolls back, so a second run of a non-idempotent script duplicates layers, re-applies `moveTo` and writes keyframes on top of keyframes (issue #43). The guidance to prefer few large scripts makes the ones most likely to be re-run the most destructive to re-run. `__rjResult` therefore wraps *any* null — `undefined` and an explicit `return null` alike — in `{ok:true, returned:null, undoGroup, note}`. A returned value still comes back bare, falsy ones included; the envelope is for nothing, not for falsy.

- **`run_jsx`'s error line counts from something the caller cannot see.** The reported number did not map onto the submitted script and the shift was not even constant between calls — the same "line 22" pointed at two different statements in consecutive calls (issue #46). It costs more here than anywhere else: nothing rolls back, so an agent that cannot locate the throw either reads the whole project back or, worse, runs the script again and applies the completed half twice. Two things fix it, and the second is the one that survives being wrong. First, the caller's line 1 is a **counted** distance down the evaluated source: `__RJ_WRAP_PREFIX` carries no newline, and `__rjBuildSource` measures the preamble it actually built rather than asserting a constant — which matters now that `libraries` are inlined into that preamble and its length changes per call. Second, the failure is reported with the line's **text**, which needs no trust in any numbering, and `__rjSourceInfo` refuses to map a line that falls outside the script rather than clamping it — a confident wrong number sends the reader to a statement that did not fail; a line that lands in an inlined library is attributed to that file by name instead. `aeErrorText()` in `util/errors.ts` is the one place this becomes prose. `tests/unit/run-jsx-lines.mjs` holds the preamble invariant, with and without libraries; nothing else can, since there is no ExtendScript to run offline.
- **`Error.start` and `Error.end` are 0 on every ExtendScript error in AE 2026, and 0 is not an offset.** The documentation presents them as character offsets into `Error.source` — a better answer than `Error.line`, because they need no assumption about what `line` counts from. Probed inside AE, catching from a four-line script that throws on its last line: `eval("(function(){ var a=1;\nvar b=2;\nvar c=3;\nnope.boom();\n})()")` → `{ "line": 4, "start": 0, "end": 0, "srcLen": 57 }`. **`line` is already correct.** The offsets came back 0 however far into the source the throw was, so reading them as offsets put *every* failure on line 1, printed line 1's text, and demoted the true number to the parenthetical afterwards — which is how #46 was reported fixed while every error still said line 1. The branch is kept but guarded: `start === 0 && end === 0` means After Effects declined to say, not that the error is at character zero, and only a non-zero start (or a zero start with a non-zero end) is believed. Do not restore it from the documentation. `tests/unit/run-jsx-lines.mjs` carries a stub built from that probe — the old stubs all omitted `start` entirely, which is exactly why they were green.
- **`app.executeCommand()` silently no-ops through the bridge.** `app.executeCommand(2080)` (Edit → Duplicate) runs, throws nothing, and does nothing: menu commands need host/panel focus and an active selection, and CEP's `evalScript` guarantees neither. It fails in the worst available shape — a success result for work that did not happen — and only surfaces later as a missing item. There is nothing to fix in code, so the `run_jsx` description names the failure and points at the API equivalents (`CompItem.duplicate()`, `layer.duplicate()`). Reported as issue #47.
- **`$.evalFile` does not evaluate at global scope — it evaluates into the calling function's scope, exactly as `eval` does.** The whole first design of `run_jsx`'s `libraries` rested on the documented claim that it does: the server sent `{path, hash}`, the panel `$.evalFile`d each file from a loader function, and the promise was "load once, call for the rest of the After Effects session". Probed inside AE 2026, calling `$.evalFile` from the body of an eval'd script on a library declaring `function rig2()` and `var RIGVAR = 3`: `{"exists":true, "typeofRig2_local":"function", "typeofRIGVAR_local":"number", "globalRig2":"undefined", "viaGlobal":null}`, and on the next `run_jsx` call in the same session `{"typeofRig2":"undefined", "viaGlobal":"undefined"}`. Everything a library defined lived inside the loader and was gone before the wrapper ran, so `libraries` answered `Function rig is undefined` every time, for every library, in every session — and the per-session hash cache only ever skipped work whose result had already been discarded. The library source is now **inlined into the same eval as the caller's script**, ahead of it, which is the only arrangement that puts a library's declarations in the script's scope. Three things follow and all three are handled rather than left to surprise someone: the server sends `{path, text}` because the panel now needs the bytes, not a path (context is saved in the *conversation*, which the server-to-panel hop was never part of); a library is re-evaluated on every call, so libraries are for declarations, not for work; and the library text shifts the caller's line 1 down, which is #46's exact failure mode, so `__rjBuildSource` counts the preamble it built and hands it to the mapping. A library is also parse-checked on its own — `eval("(function(){ " + text + "})")`, never called — before it reaches the shared eval, because a missing brace in a library otherwise takes the whole wrapper down at whatever line AE's parser gave up on, frequently a line of the caller's script.


## Undo groups

- **An undo group does not survive an `evalScript` boundary. Measured, and it costs three releases of a false guarantee.** `app.beginUndoGroup(name)` in one `evalScript` call and `app.endUndoGroup()` in a later one does not produce one undo step — After Effects **discards** the group, and every write inside it lands as its own step with its own AE-generated name. The evidence, gathered against AE 2026 while verifying 0.4.0 (issue #69): a 600-op `run_batch`, which opened its group in `run_batch` and closed it from the last `_continue_job`, produced **~600 undo steps**; one Cmd-Z took the comp from 601 layers to 600 and the Edit menu read `Undo New Solid`, not the batch's group name. A controlled probe — begin in one call, write in a second, end in a third — reproduced it on its own. Nothing raises, nothing warns, and the return value of `endUndoGroup()` is the same either way, so the only way to see this is AE's Edit menu.

  Two consequences are permanent. **Every group must open and close inside one call**, which is why `run_batch` is one group inline and one group per chunk when chunked, and why `core.jsx` funnels every `beginUndoGroup` through `__beginUndoGroup` and counts them — the `undoSteps` a batch reports is the counted delta, so the number an agent repeats to a user as "press Cmd-Z N times" is measured rather than intended. And **a design that needs a group to span calls cannot have one**: `singleUndo:true` buys the single step back only by giving up the chunking entirely, blocking AE for the whole batch, which is a real cost and is stated in the tool description rather than hidden.

  This is the third bug in this release traced to Adobe's documentation asserting something AE does not do — `CompItem.posterTime` and `exportAsMotionGraphicsTemplate`'s surviving object references are the other two. **Undo behaviour, like `saveFrameToPng`, is measured against a live AE before it is claimed anywhere.** `tests/unit/batch-undo.mjs` cannot see AE's undo stack, so it asserts the property that decides it: no dispatch call ever returns with a group still open.

- **`run_jsx`'s undo group collides with `copyToComp`.** AE refuses to copy a layer that has a parent or a linked expression while an undo group is open, so `dispatch()`'s wrapper broke exactly the rigs worth copying (issue #30). `run_jsx` now takes `undoGroup:false`, resolved per call through the predicate form of `__meta.noUndo`, and `core.jsx` exposes `withoutUndoGroup(fn)` for closing the group around one statement. Keep the opt-out on the handler's `__meta` — dispatch must stay stateless between calls, or one op's opt-out leaks into the next.

- **FIXED (2026-10-12): a screenshot no longer buries the user's last edit under steps of its own.** A screenshot renders by changing things and putting them back — `CompItem.resolutionFactor` for every capture, and for `screenshot_layer` every solo flag and an optional background solid — and both ops are `noUndo`, so each assignment used to land as its own AE step. Measured before the fix (recipe 64, the user reading Edit > Undo): a single frame cost **2** "Resolution Change" steps, a 2-tile sheet 4, a 4-tile sheet 8 (an empty tile included; the 7 the trial in recipe 62 counted was not reproduced), `screenshot_layer` 4 (two "Toggle Switch" around two Resolution Changes) and with a background **8** — Toggle Switch, New Solid, Layer Reordering, two Resolution Changes, Clear Layer, Remove Item, Toggle Switch — where stopping part way put the temporary solid back into the comp with the target soloed. Two more measured facts shaped the fix: **assigning the resolution the comp already has still records a step**, and assigning an unchanged solo does not. Now (`vision.jsx`, `__shotCapture`): nothing is assigned that would not change, the factor is set once per contact sheet rather than per tile, and the first change a capture makes opens ONE group, "AE MCP: screenshot (view only)", closed after everything is put back inside the same `evalScript`; inside a caller's own group (a `run_jsx` script calling `OPS.screenshot_frame`) none is opened. Measured after (recipe 65): a capture at the viewer's own resolution adds **no step**; every other case — single frame, 2- and 4-tile sheets, `screenshot_layer` with and without a background — exactly **one**, and undoing it left resolution, every solo flag, the layers and the project items as they were before the capture (the background's Solids folder included), with the user's write next in line. Every capture reports what it did (`undo` on the result: groups opened, temporary changes, whether all of it was read back as restored, anything left in the project), and the panel's note claims no more than those reports support — `allRestored` is null, not true, when any attempt never reported; restored settings and leftover items are stated separately; and "undoing it changes nothing" is said only when everything was restored and nothing was left. The panel adds up every capture a request ran — its stale-frame re-render and a sheet's per-tile re-render included — onto the image, the empty-frame result, the sheet, or the error text. It reports groups *opened*, not Edit-menu steps: one group was one step in all five cases measured, but a request with a retry was not measured live, nor was a capture inside a caller's group. Never "fix" this by purging AE's undo history: that destroys the user's own editing history to hide ours.

## Keyframes, easing and expressions

- **`setTemporalEaseAtKey`'s array length belongs to the property, and cannot be read off the value.** Spatial properties (Position, Anchor Point) take a single entry regardless of 2D/3D, because the ease runs along the motion path. Everything else has to be measured, because the count and the value's own length disagree in *both* directions — and the two properties that prove it were documented the other way round for a release, each reading individually plausible, until a live pass measured them. **The measured arities are the `extendscript-gotchas` guide topic's to state, not this file's**: keeping a second copy here is how the resident copy went stale while the guide's stayed right. What belongs here is why the code trusts no table at all — `__applyTemporalEase` derives a count and then still walks a 1-2-3-4 ladder on failure: the derivation is the fast path, not the authority, and the arity it settles on comes back as `easeDimensions` so a caller learns the real answer instead of the documented one. Issue #96 adds a single unreproduced observation — a 2D layer's Position accepting only 3 through raw `setTemporalEaseAtKey` on 26.3 — which is one more reason the ladder, not the table, is the authority. The table has exactly one home, `packages/mcp-server/src/guides/extendscript-gotchas.md`; `animation.md` points at it and must not restate it, and neither may this entry.
- **Assigning `Property.expression` succeeds whatever the text says; `Property.expressionError` is where AE reports that it does not run.** A syntax error or a bad reference throws nothing on the assignment — the failure is a warning banner in the AE UI that an agent cannot see, and until 0.5.0 `set_expression` returned `{ok:true}` for it and `get_expression` never read the field (issue #97). The skill recommends expressions over dense keyframes for anything procedural, so this was the gap between the advice and what could be verified. `__expressionError` in `expressions.jsx` reads the field after **forcing one evaluation** by reading `prop.value` inside a try: Adobe's documentation implies the field is populated when the expression is evaluated, and whether 26.3 fills it in on a bare assignment is not something an offline test can settle, so the nudge makes the answer independent of the question (a group throws on `.value`, which is not an expression error, and an AE without the field reads as no error — both handled). `set_expression` and `toggle_expression({enabled:true})` throw with the path, AE's own message and both ways forward, and say the expression *stays written*: nothing here rolls back, and a caller fixing a typo wants the property it aimed at, not a cleared one. `get_expression` carries `expressionError` alongside `expression` and `enabled`. `tests/unit/expression-error.mjs` has a mock that hides the error until `.value` is read, so a guard that only reads the field fails there. Measured on 26.3x87 (recipe 39, 2026-09-08): the field is populated on assignment, before `.value` is read — the nudge is belt-and-braces there, kept because it costs one read and covers the documented case.
- **Removing the last Time Remap key hides the property.** `while (tr.numKeys) tr.removeKey(1)` on a remap-enabled layer leaves `setValueAtTime` throwing `the property or a parent property is hidden` (issue #86). Setting `timeRemapEnabled = true` already creates the two keys a loop needs, so anything in this repo that builds a loop — a bed in `audio.jsx`, say — edits those keys in place and never clears them; toggling `timeRemapEnabled` off and on restores the defaults.

## Shapes

- **Shape `Contents` renders index 1 in front, and `addProperty` appends to the end.** So the *first* node added is the one on top, which is the opposite of the layer stack, and building back-to-front (body, then title bar, then dots) produces a silent solid slab with no error. The fix an agent reaches for is worse than the bug: `property.moveTo()` looks correct when the comp is rendered standalone and leaves it serving a stale buffer in every **nested** render. `add_shape_content` therefore takes `zOrder` rather than an index — `"back"` is the append AE already does and touches nothing, and `"front"` is the single `moveTo(1)` call site in the codebase, done on the empty node before any property is set so a failure costs an empty node. The guidance everywhere (tool description, guide) is to order the calls front-to-back and never need it. Reported as issue #32; if `moveTo` is ever proven safe, the note in the description comes out, not the option.
- **`moveTo` is a `PropertyBase` method, and a `Layer` is not a `PropertyBase`.** It re-ranks a property inside an indexed group; called on a layer it throws `parent is not an INDEXED_GROUP`, which is what every `reorder_layer` call did from the day the op shipped until 0.4.0 (issue #70). Nothing caught it because nothing offline ran the op, and the error names a concept — an indexed group — that has no counterpart in what the caller asked for, so an agent hitting it at the moment it is trying to fix a layer stack has nowhere to go. Layers reorder with `moveBefore` / `moveAfter` / `moveToBeginning` / `moveToEnd` — the first two take a **layer**, the last two take nothing at all, and none of the four takes an index. The one legitimate `moveTo` in this codebase is the shape-property `moveTo(1)` in the bullet above; `tests/unit/reorder-layer.mjs` gives its mock layer a `moveTo` that throws AE's own message, so a rewrite that reaches for it again fails there rather than in someone's project. Related: because reorder is the op that invalidates every index below it, `reorder_layer` takes `beforeLayerId` / `afterLayerId` as well as `toIndex`, and `toIndex` is documented as the index the layer **lands on** — moving up and moving down need different primitives and the two readings differ by one, silently.
- **A shape node reference goes stale when a sibling is added.** Hold a Fill, add a Stroke to the same group, and the Fill reference starts throwing `Object is invalid`. Add every node first, then re-fetch by name before setting values or expressions. `add_shape_content` re-fetches from the parent after its own `moveTo` for exactly this reason. Reported in issue #24.
- **A new shape layer's origin is now `[0,0]`, not AE's comp centre — and that is a deliberate behaviour change.** `addShape()` leaves Position at the comp centre with the Anchor Point at `[0,0]`, so layer space is offset from comp space by half a frame. Every path this toolset can write — `set_shape_path` vertices, `add_shape_content` vertices, a rect or ellipse `position` — is in *layer* space, while every other coordinate an agent handles (comp size, `sourceRect`, other layers' positions, a screenshot) is comp space, and nothing in the old response said which one it had been given. So a drawing authored in comp pixels came out shifted by `(width/2, height/2)`, and the check that would catch it is a downsampled screenshot: issue #51 cost a review round. `create_shape_layer` therefore takes `position`, defaulting to `[0,0]`, which makes the two spaces the same space; `"center"` is AE's own spawn point kept to one word, and the result echoes the position and anchor point it ended up with so nobody has to render a frame to learn the coordinate system. **What this breaks:** a caller that relied on the old spawn point to centre a motif — `create_shape_layer` then `add_shape_content({type:"rect", size:[200,100]})` with no explicit position — now gets that rect at the top-left corner instead of the middle. The fix is one argument (`position:"center"`), the failure is visible in the first frame rendered rather than three edits later, and the precedent is the `anchorAlign` change in 0.2.1: this repo changes a creation-time default when the old one was wrong in a way that only shows up downstream. `tests/unit/shape-spawn.mjs` holds the default, the escape hatch and the echo.
- **AE hangs a 48-property `ADBE Vector Materials Group` off every vector group, and it is inert on a 2D shape layer.** It is the 3D extrusion model — Front/Bevel/Side/Back × twelve attributes — and it only means anything for an extruded shape under the Cinema 4D renderer. It was around 75% of the bytes of a shape read: one 68×68 circle in one group cost 4,400 tokens, of which the geometry was about 40 (issue #42). `explore.jsx` skips it unless `shapeMaterials` asks, which is the one place `include`-absent-means-everything does not hold — hence `materialsOmitted` and a note in the response, and hence a separate flag rather than a member of `include`, whose contract would otherwise have to bend. The group Transform beside it is elided by the same walk when every property is still at its creation value, tested against `__VECTOR_TRANSFORM_DEFAULTS` rather than through `PropertyBase.isModified`: the values can be asserted with no AE to run in, and a property that table has never heard of has to fail the test rather than be folded away unread.


## Text

- **Text alignment is justification, never a computed anchor.** `addText()` centre-justifies point text with the anchor at the origin, so the visible left edge sits at `-width/2`. Until 0.2.1 `create_text_layer` implemented `anchorAlign` by measuring `sourceRectAtTime()` and writing that offset into the Anchor Point. It renders identically at creation and is wrong from the first edit onward: the offset is baked for the string that existed then, so retyping, an expression on Source Text, or an Essential Graphics edit in Premiere re-centres the text on a stale anchor and the layout jumps — and any `sourceRectAtTime()` expression sizing a background behind it inherits the error. `anchorAlign` now sets `ParagraphJustification.LEFT/CENTER/RIGHT_JUSTIFY` (the map lives once, in `text.jsx`) and leaves the anchor at `[0,0,0]`, which is live for whatever the layer says later. Reported as issue #24. `"none"` still means "touch nothing".
- **`addText()` inherits the user's Character panel.** Tracking especially: a layer created with no styling arrives at whatever that workspace was last left on — the report that opened #24 measured `-20` — so the same call renders differently on two machines. Nothing in this repo ever set it. `create_text_layer` now writes tracking explicitly (`args.tracking`, or 0), which is the only way to make the tool reproducible; `anchorAlign: "none"` opts out along with everything else.
- **The TextDocument round trip can lose the justification, and nothing says so.** Two reports against AE 26.3, and the mechanism of neither is known. `set_text({text})` on a layer that read LEFT_JUSTIFY (7413) came back CENTER (7415) — the handler reads `src.value`, changes `.text` and writes the same document back, so it is the round trip itself, not a fresh document, that drops it (issue #93). And a script assigning `CENTER_JUSTIFY` through the TextDocument stored RIGHT (7414) while `set_text({justification:"center"})` on its own landed correctly (issue #94). Neither raises, and a layer that silently re-centres is found half a frame off in a screenshot several edits later. The guard that can be built blind is the one this repo asks for anyway: **`__verifyJustification` in `text.jsx` reads the property back after every round trip** and compares it with what should be there — the requested value, or the one read before the mutation — writes the justification alone once more if it moved, and throws naming expected and actual if it still disagrees. `set_text` and `create_text_layer` both go through it (the create path removes the layer it made before throwing, so a failure never leaves a layer the caller has no id for), and both return `justification` by name plus `justificationReasserted`, which is the only way a live run can show whether the reset actually happens. `tests/unit/text-justification.mjs` models both reports as pluggable misbehaviours on a mock Source Text; which of them AE 26.3 actually is, recipe 38 measures — and on 26.3x87 (2026-09-08) *neither reproduced*: `set_text({text})` on a LEFT layer read LEFT back with `justificationReasserted: false`, and `create_text_layer` with `anchorAlign: "center"` and a non-default font landed `center` first time. Both reports were against 26.3, so the guard stays. If the reassert is measured to land reliably, keep it — one extra `setValue` is cheap and the read-back is the contract; if it is measured *never* to land, the mechanism is worth finding before anything else is changed.
- **`TextDocument.justification` written from a script stores the wrong value.** On 26.3, `d.justification = ParagraphJustification.CENTER_JUSTIFY; prop.setValue(d)` lands as RIGHT (`7414`) on a layer made with `addText()`, while the enum reads correctly in that scope; LEFT only appears to work because it is `addText()`'s default (issue #94). `text.jsx`'s own justification map lands correctly, so the tool path is unaffected and the raw path is documented in `extendscript-gotchas.md` under Text, with the `sourceRect.left ≈ -width/2` check. If `set_text` ever starts landing RIGHT for `center`, this is where to look first.

## Audio

- **`layer.property("ADBE Audio Levels")` returns null on an audio layer.** Audio Levels sits inside the layer's `Audio` group, not on the layer, and the only reliable handle is the `layer.audioLevels` shortcut (issue #48). A null there does not throw — it just means the level is never set, on every layer, silently — which is most of the reason `place_audio_cues` exists rather than being left to a `run_jsx` loop. `audio.jsx` uses the shortcut and falls back to the group walk; if neither answers it says so instead of leaving a layer at whatever level the file happened to have. AE's Audio Levels is itself in decibels, two channels, and the tool writes `0` explicitly when the caller gives no level for the same reason `create_text_layer` writes tracking explicitly.
- **A batch op has to be all-or-nothing, because a partial one cannot be described.** `place_audio_cues` can be handed 90 cues; a run that dies on cue 30 leaves 29 sound effects in the timeline and an error naming none of them, and the natural next move — call it again — doubles the first 29. So it plans the whole list with no side effects (resolving every `footageId`, checking every path exists, checking each resolved item has audio, checking every time is inside the comp), reports *all* the offending cue indices at once, and creates nothing if any of them failed. What planning cannot foresee — an import that turns out to be silent, an AE refusal on some particular layer — is caught by a rollback that removes every layer and every import the call made, newest first, layers before items. **The layer joins the rollback list the instant `layers.add()` returns, not once it is configured**; registering it after the last `setValue` leaves exactly the failing layer behind, which the offline test caught before this ever ran in AE. `dryRun:true` is the same planner with the creation phase skipped, and it is not an undo step either — a plan appearing in the user's undo history would make "this changed nothing" false in the one place they can see it.
- **Each of `place_audio_cues`' per-cue options moves something After Effects then quietly resets, so the statement order in `__placeAudioCue` is load-bearing.** `layer.stretch` moves the layer's start time (reported in #85; with the re-assertion in place a stretched cue lands with `startTime` and `inPoint` both at the cue time — measured 2026-09-08: `{time: 5, stretch: 200}` on a 0.3s file → startTime 5, inPoint 5, outPoint 5.6 — while which point AE holds *without* it was not isolated; the mock in `tests/unit/audio-cues.mjs` moves it so a version that forgets the re-assertion fails), so `startTime` is set after it and the trims after that. `timeRemapEnabled = true` resets the out point to the file's own end, so a looped cue's end — the caller's `outPoint`, or the comp's — is re-asserted after remap is enabled, and set *before* the in point: an in point past the file's natural end can only land once the layer is allowed to extend, which is also why the out point goes first on an unlooped cue. **The two Time Remap keyframes AE creates on enabling stay exactly where they are.** Removing every key hides the property, and the next `setValueAtTime` on it throws (issue #86); the loop expression overrides them anyway, so there is nothing to gain. Fade keyframes go last, at the in/out the layer *actually* has, on `layer.audioLevels` — the #48 handle — and Time Remap is reached through `layer.timeRemap` for the same reason, since `layer.property("ADBE Time Remap")` is null on an audio layer even after enabling. `canSetTimeRemapEnabled === false` refuses by name; an undefined does not, on the `hasAudio` principle.
- **The loop expression is the `%` pattern issue #85 measured, with two deliberate substitutions, and one constant that can go stale.** `(time - startTime) % thisLayer.source.duration`: `startTime` in place of the issue's `inPoint`, so a trimmed in point hides the front of the file the way a trim does on every other layer instead of delaying the loop's first cycle; and the duration read live off the layer rather than baked, so a relinked file keeps looping. An expression cannot read a layer's stretch, so a looped *and* stretched cue has `* 100 / <stretch>` baked in — change the stretch by hand afterwards and the loop keeps the old rate, which the tool description says. `loopOut("cycle")` on the remap keys would survive that edit natively and is the thing to swap in if a live pass ever shows the `%` form misbehaving; it was not chosen because its last key sits at the file's end, which for audio is one frame of silence per cycle. A fade's fit is measured against the cue's *placed* length, and `__fadeFitProblem` is pure so it can run twice: at plan time wherever the length is already known (a `footageId`, a reused item, a capped `outPoint`, a loop's chosen end) and again after the imports for the files it had not seen — still before any layer exists, so a misfit names every offending cue at once and costs only the imports, which the rollback takes back. `-48` is the default `fadeFloorDb` because it is the bottom of the range AE's own Audio Levels slider offers and 1/256 of the recorded amplitude. **What no offline test can hear or see:** that AE 2026 accepts `startTime`, `thisLayer.source.duration` and `%` on a Time Remap expression and plays the bed past the file's length; the fade being audible on a RAM preview; stretch changing pitch; and which point AE holds when `stretch` is set — recipe 40.

## Motion Graphics templates

- **`exportAsMotionGraphicsTemplate` invalidates every reference held across it.** Not just the `CompItem` — `app.project` too. Measured on 26.3: after a successful export, a `comp` captured beforehand throws `Object is invalid` on `.name`, and so does an `app.project` captured beforehand, while a fresh `app.project.itemByID(id)` returns a working comp. The first version of `export_mogrt` built its result object from the pre-export `comp` and therefore threw *after* writing a perfectly good `.mogrt` — reporting a failure for work that did happen, which is the same class of lie as swallowing an error. `mogrt.jsx` captures `id` and `name` as primitives before the call and re-fetches after it. Nothing about the error says which object went stale, so if a mogrt op ever starts throwing `Object is invalid`, look for a handle held across the export before anything else.
- **`app.beginSuppressDialogs()` is what makes a scripted `.mogrt` export usable, and it was worth measuring.** Issue #23 filed it as untested. It is not: with a comp using a non-Adobe font, the export returns in ~3s suppressed and blocks past 60s unsuppressed, writing nothing until someone clicks OK on "The following 1 fonts were not synced from Adobe". `endSuppressDialogs(false)` must run in a `finally` — leaving dialogs suppressed would silence every warning for the rest of the user's session.
- **Suppression costs the only channel AE has for saying why, and that silence must never be read as a dialog.** `exportAsMotionGraphicsTemplate` answers with a bare boolean, so under `beginSuppressDialogs()` a refusal and a success-that-wrote-nothing are indistinguishable from a script. The old failure message filled that gap by naming a modal dialog — and the case that exposed it was a comp with an **empty Essential Graphics panel**, which AE simply will not export: no file, no dialog, no word of explanation. The user was sent to click something that did not exist while the real fix, adding one controller, went unmentioned (issue #71). Under suppression a blocking dialog is the one cause ruled out *by construction*, since suppressing them is precisely what the call did, so the message may not name one there; unsuppressed, it is the first thing to look at. Everything else reports as **unknown**, and the diagnostic offered is the one that actually reaches AE's own reason — the user running the same export by hand from the Essential Graphics panel, where AE shows its error in the UI. Same shape as `BridgeTimeoutError` vs `BridgeUnreachableError`: two failures, opposite remedies, no shared sentences.
- **So `export_mogrt` checks every precondition it can *before* exporting, and refuses naming it.** `motionGraphicsTemplateControllerCount === 0` is the one from #71; the project having never been saved, a name that resolves outside the destination folder (measured through `File.parent`, not a list of illegal characters — `packages/jsx/*.jsx` may not branch on platform), a blank name, a destination that refuses a write probe, and a name collision are the others. All of them run before the project is touched at all: no rename, no `app.project.save()`, no export attempt, so a refusal costs the user nothing. Two rules hold it honest: **only an explicit `0` refuses** — a controller count the host will not answer comes back `null` and exports anyway, because an unanswered question becoming a confident refusal is the same mistake pointed the other way; and the refusal message for the empty panel contains the word "dialog" nowhere at all, denials included, since naming one is what sent people looking. `tests/unit/mogrt-preconditions.mjs` covers the lot, including that `endSuppressDialogs` still runs when the export itself throws.
- **The `.mogrt` filename comes from `comp.motionGraphicsTemplateName`, not the comp name**, and it defaults to the literal `"Untitled"` for a template assembled by script. Left alone, every export in a project overwrites the same `Untitled.mogrt`. `export_mogrt` defaults it to the comp name but leaves a name the user actually set alone. Related: `CompItem.posterTime` does not exist (the thumbnail is the comp's first frame, hence the black one on anything that fades up), and there is no `getMotionGraphicsDataName` — only the reverse-indexed `setMotionGraphicsControllerName`.

## Comps, footage and project items

- **AE fabricates dimensions for an SVG with a very large viewBox, and the numbers depend only on the viewBox.** A synthetic file with the reported `0 0 278050 333334` imports as **15906x5654** — byte for byte the dimensions in issue #33, from an entirely different SVG. It will not even rasterize: `saveFrameToPng` on a comp containing one produces no file at all, where a healthy SVG renders in seconds. That reproducibility is what makes the aspect-ratio check in `footage.jsx` a reliable detector rather than a heuristic.
- **`CompItem.duplicate()` is shallow, and the copy looks finished.** The
  duplicate's precomp layers point at the *same* nested comps as the original,
  so "make a variant of this rig" and then editing the variant edits the
  original too — silently, and usually noticed several scenes later.
  `duplicate_comp` keeps that as the default because it is AE's own Duplicate
  and changing it would surprise anyone who knows the app, but it says so in the
  result rather than leaving it to be discovered, and `deep:true` duplicates the
  nested comps and re-points the copy at them. Two things `deep` has to get
  right and a hand-rolled `run_jsx` version usually does not: the same nested
  comp appears on several layers, so it is duplicated once and reused (keyed by
  the *original* id) rather than fanned out per reference; and the copy is
  registered in that map *before* the walk descends into it, which is what makes
  a cycle terminate. A nested duplication that fails part-way names every comp
  it created in the error — the objects are real and nothing rolled them back.
- **A solid's footage item outlives every layer that used it, and `delete_comp` used to leave all of them behind.** `layers.addSolid()` makes two things: a `FootageItem` whose `mainSource` is a `SolidSource`, filed in the project's Solids folder, and a layer pointing at it. Removing the comp — or the layer — removes only the layer. Nothing warns, and once orphaned the item is indistinguishable in the Project panel from a solid still in use unless something reads `usedIn`. A verification pass that built and discarded test comps left **1,863** of them to sweep out by name (issue #83). Two things fix it, and the scoping of the first is the whole point. `delete_comp({purgeUnusedSolids:true})` collects the solid items from the deleted comp's **own layers** before the removal and afterwards removes only those whose `usedIn` is empty — deleting comp A must never reach a solid that only some other comp uses, and an unused solid that was never A's is someone else's work in progress, not this call's to judge; a shared one is kept and reported with the comps keeping it. It is off by default because a solid can legitimately be shared, and the default result counts what it left (`unusedSolidsLeft`) so the orphan is visible at the moment it is made. `purge_unused_footage` is the project-wide sweep — AE's own Remove Unused Footage with a `dryRun` and a report — and it decides by two tests, both `instanceof`: `FootageItem` (a `CompItem` is also an AVItem with a `usedIn` of its own, and a nested comp nothing uses any more is exactly what a naive sweep deletes) and, by default, `SolidSource` on `mainSource`. Both ops collect in one pass and remove in a second, highest project index first, and both stop at the first `remove()` that throws and name it, what went before it and what was never attempted, because nothing rolls back. The dry run lists in the order the real run removes, so the plan is the truth about order too. `tests/unit/purge-footage.mjs` holds all of it; what it cannot hold is whether `usedIn` already reads empty in the same `evalScript` as the `comp.remove()` — recipe 35 is that measurement, and on 26.3 it does (measured 2026-09-08).
- **OPEN (2026-10-12): the Solids folder outlives its last solid.** AE files a new solid in a `Solids` folder it creates on demand, and nothing here removes that folder once it is empty. Seen twice on 26.5: `delete_comp({purgeUnusedSolids:true})` removed a null's solid and left the empty folder (recipe 62), and `screenshot_layer` with `background` removed its temporary solid and left an empty `Solids` folder in a project that had none (recipe 63). `delete_project_item` in `safe` mode removes it. A screenshot now names that folder in its `undo.leftBehind`, and undoing the screenshot's one step removes it with the rest (recipe 65). Not fixed, and not trivially fixable: a user may keep their own `Solids` folder (empty or not), so a fix may only remove a folder the same call created, or emptied of items the same call removed — a design question before it is a code change.

## The Project panel hierarchy

Measured on **26.5x89**, 2026-10-11, in disposable items (recipe 53). These are why `project.jsx` is shaped the way it is.

- **Ids are the only identifier.** A `ProjectItem.id` survives rename and move, while names repeat freely (two folders "Twin", two comps "Twin comp", and `""` are all legal) and `project.item(i)` walks in Project-panel order — by name, depth-first — so an index moves when anything is renamed. Every C2 op takes ids; names are display text. `get_project_tree` sorts explicitly (case-insensitive name, exact name, id) instead of exposing AE's order.
- **The root is a folder that does not behave like one.** `rootFolder` is a `FolderItem` with id 0, absent from `project.items`; `itemByID(0)` throws "Item Not Found", `remove()` says "Can not remove the root folder", and setting its `parentFolder` is refused — but a script *can* rename it, and the Project panel has no way to name it back. So 0 means "the root" as a destination and is refused as the thing to rename, move or delete. `project.numItems` counts items at every depth; a folder's `numItems` counts its direct children.
- **`parentFolder` is writable for every item and takes only a `FolderItem`** — a comp or `null` is "not of the correct type". A folder moves with its contents. AE refuses a folder moved into itself or a descendant, but as `internal verification failure {parent_folder_itemH must be different from itemH}` or "a folder cannot be moved inside itself"; `move_project_item` checks ancestry by id first and names the cycle's path.
- **`remove()` never asks, and it reaches past the item.** A non-empty folder is deleted with everything inside it, recursively — nothing moves up to the parent. Footage a layer uses is deleted *with the layer*, in every comp; a comp used as a precomp takes its layers in the other comps; a queued comp takes its Render Queue item; a folder holding an in-use solid takes the solid and the layers using it. No dialog, no warning, at any depth. Hence `analyze_project_item_deletion` (read-only, the full consequence) and `delete_project_item`, which refuses anything whose deletion would reach a layer in a comp that is not itself being deleted, or a Render Queue item — in every mode. `safe` allows an empty folder or an unused comp/footage item; `recursive` adds a folder's whole contents, only when nothing outside it uses any of them. After a deletion every removed id is re-checked, and the project's item count, Render Queue length and the layer count of every surviving comp are compared with the analysis; a mismatch is an error, never `deleted:true`. Expressions that name a deleted comp are not detected.
- **An empty `Solids` folder deletes cleanly, and AE makes a new one** (a new id) the next time a solid is created. `delete_project_item` in `safe` mode is the typed way to clean one up.
- **No `locked` flag exists on project items**; `id` and `typeName` are read-only. Deleting the comp open in the viewer is allowed and leaves `activeItem` null.
- **Undo is unmeasured.** Each write runs in one undo group through `dispatch`, but a script cannot invoke Undo over this bridge, so whether one Cmd-Z restores a recursive folder deletion exactly — every descendant, in place — has not been verified and needs checking by hand in After Effects.

## Layers and transforms

- **An enum looked up by a name AE does not define is `undefined`, and every assignment written as `X[name] || current` turned that into a silent no-op with `{ok:true}`.** Blend mode, track matte type and mask mode all did it. The schema now carries closed lists (`BLENDING_MODES` and siblings in `schemas.ts`) and `__enumByName` in `ids.jsx` throws for a name the running AE lacks, before the handler writes anything. The lists were checked member-for-member against `BlendingMode` (38), `TrackMatteType` (5) and `MaskMode` (7) on 26.5x89 — identical in both directions; `SILHOUETE_ALPHA` is AE's own spelling.
- **Every Transform property exists on every layer kind, and a hidden one accepts its own value back.** Measured on 26.5x89 over 2D/3D solids, a 3D null, text, shape, one- and two-node cameras and all four light types: `tr.property(m)` is non-null for all eight of Anchor Point/Position/Scale/Orientation/X/Y/Z Rotation/Opacity everywhere, and `setValue(p.value)` succeeds on every one of them. Only a *different* value throws — "the property or a parent property is hidden". So neither existence nor a trial write can tell `set_transform` whether a request will land. The hidden ones: a 2D layer's Orientation and X/Y Rotation; a camera's Scale and Opacity, plus Point of Interest (`ADBE Anchor Point`) when it is one-node; a spot light's Scale and Opacity; a parallel light everything but Point of Interest and Position; a point light everything but Position; an ambient light all eight. `canSetExpression` matches that hidden state exactly in every case **except** an ambient light's X/Y Rotation, which report `true` and still refuse — so `__transformWritable` in `transforms.jsx` uses `canSetExpression` and special-cases ambient, and `set_transform` resolves every requested property against it before its first write. A static `setValue` on a keyed property throws too, which is why the same preflight refuses that combination rather than half-applying the call.
- **A mask path's `Shape` value carries the mask's variable-width feather points** (`featherRadii`, `featherSegLocs`, `featherRelSegLocs`, `featherTypes`, `featherInterps`, `featherTensions`, `featherRelCornerAngles`). Building a fresh `Shape` to change a mask's vertices or tangents silently drops them; `set_mask` assigns onto the value it read back, which AE hands out as a copy (measured: a feather radius of 12 survives a tangent edit).
- **Cameras and lights have no `threeDLayer` switch; reading it gives `undefined`.** Anything that gates a 3D-only property on `threeDLayer` treats a camera as 2D. `set_transform` used to skip a camera's Orientation without a word for exactly that reason; `__layerIs3D` in `transforms.jsx` checks the layer class first.

- **AE's scripting DOM has no `toComp`/`toWorld`.** Those exist only in the expression language, so anything needing a world transform reimplements the matrix chain — `layers.jsx` does, for `parent_layer`'s `preserveTransform`. Two things follow: 2D only (AE's 3D rotation order is not worth guessing at), and a child's `Position` has two possible readings of its parent's space that differ by the parent's anchor point, so the position correction only fires when AE's own answer matches *neither* — the one case where AE is provably wrong.

## Property trees

Measured on **26.5x89**, 2026-10-11, by walking every property of disposable 2D/3D solids, a one- and a two-node camera, all four light types, text with an animator, a shape layer, a precomp with Time Remap on, and a solid carrying Gaussian Blur, two Glows, Fractal Noise, Curves, Gradient Ramp, Keylight and expression controls (1,350 nodes, recipe 49). `inspect_property_tree` (`inspect.jsx`) is built on these facts.

- **Groups answer `undefined` for every value-ish field** — `propertyValueType`, `value`, `expression*`, `numKeys`, `isSpatial`, `canSetExpression`, `minValue` — while `name`, `matchName`, `propertyType`, `numProperties`, `enabled`, `active`, `elided`, `isModified`, `isEffect`, `isMask`, `canSetEnabled` all answer. The layer itself is the root group (`ADBE AV Layer`, 15 children on an AV layer, Layer Styles / Geometry / Material Options among them) and its `propertyIndex` is `undefined`.
- **On properties, three fields throw rather than answer**: `.value` for `NO_VALUE` ("Can not get or set a value…") and `CUSTOM_VALUE` ("…has not been implemented"); `separationDimension` unless the property is a separation follower ("stream isn't separated"); `minValue`/`maxValue` unless `hasMin`/`hasMax`. Everything else read on all 1,159 properties. A reader that does not catch per field loses the node — which is how `list_effects` silently dropped Curves' curve and every effect section marker.
- **`PropertyValueType` has 13 members, and AE uses a 14th.** Text animator variable-font axes (`ADBE Text VF Axis 1-8`) report `1489342032`, which is in no enum; the value reads as a number.
- **Effect "sections" are not groups.** Fractal Noise's Transform / Sub Settings / Evolution Options, Keylight's Screen Matte / Inside Mask / …, are flat `NO_VALUE` properties among the parameters, and the convention differs per effect: Fractal Noise ends a section with an unnamed marker, Keylight repeats the section name at both ends, Gradient Ramp has an unnamed marker with no start (its Swap Colors button), Keylight's "About" and "Colour Balance Wheel" are buttons. Nesting cannot be inferred from them without being wrong somewhere, so the tool lists them in order, unreadable, and infers nothing. The one real nested group in every effect is `ADBE Effect Built In Params` (Compositing Options: Effect Opacity, GPU Rendering, a Masks group).
- **A marker property's `value` is a plain object, not `instanceof MarkerValue`**, and so is `keyValue(k)` — duck-typed reads (`comment`, `duration`, `chapter`, `eventCuePoint`, `protectedRegion`, …) work on both. Markers are the property's keys.
- **Every keyframe accessor answers on 26.5**: `keyInTemporalEase` (one entry per dimension: 3 on Scale, 1 on spatial Position), `keyRoving`, `keyTemporalContinuous`, `keyTemporalAutoBezier`, `keySpatialContinuous`, `keySpatialAutoBezier`, `keyLabel`, `keySelected`.
- **Separated dimensions are siblings with their own matchNames**: `ADBE Position` (leader, `canSetExpression: false`) and `ADBE Position_0/_1/_2` (followers, `separationDimension` 0/1/2, `separationLeader.matchName` = `ADBE Position`); `walkProperty` resolves `["ADBE Transform Group","ADBE Position_0"]`.
- **Named groups carry slots that are not "there".** A text animator's `ADBE Text Animator Properties` always holds all 103 animatable properties, whichever one was added; the inert ones refuse a value ("hidden"). The same is true of a 2D layer's Orientation, a camera's Scale, a disabled Time Remap, a light's falloff with falloff off.
- **`canSetExpression` is not a writability signal outside the Transform group.** Write-testing 677 numeric leaves: 298 said `true` and refused a value (every property of a layer style that is off), 22 said `false` and took one (text More Options, shape Blend Mode / Composite / Fill Rule, Keylight's View). The one rule with no false positive across 1,125 write-tested properties is `canSetExpression === false && canVaryOverTime === true` ⇒ AE refuses a value — and only within the numeric/colour value types: a Marker property also matches it and takes markers fine. Recall is poor (the layer-style case is invisible to it, and no ancestor `enabled` flag gives it away), so `inspect_property_tree` reports it as `hidden: true`, a one-way hint, and never claims a property is writable.
- **Duplicate matchNames occur only under indexed groups** (two Glows in Effects, two Fills in a shape's Contents). `property("ADBE Glo2")` returns the first, so a path that must reach the second has to use the index; `inspect_property_tree` emits a matchName segment when it is unique among siblings and the index when it is not, with `occurrence`.

## Static property writes

Measured on **26.5x89**, 2026-10-11, by writing representative properties of disposable shape, text (2D and 3D), camera, spot light and precomp layers — Transform, shape Rect/Fill/Path, a mask, two Glows, Fractal Noise, Curves, Keylight, Stroke, Set Matte, a text animator, Time Remap, a layer style — with `setValue` and reading every one back (recipe 50). `set_property_values` (`propwrite.jsx`) is built on these facts.

- **A write that does not throw has not necessarily landed.** A 2D layer's Position, Scale and Anchor Point take a third number and keep their own Z (`[100,50,7]` reads back `[100,50,0]`); a colour written as three numbers resets alpha to 1; Fractal Noise's Fractal Type stores 2.5 as 3 while a shape Fill Rule stores 1.6 as `1.60000002384186`, so "integral" parameters round in some places and not in others. Every write is read back and compared, numbers within float32 storage error (0.2 reads `0.20000000298023`). The 2D Z case is refused before the write, naming the Z to keep; the colour case sends the current alpha explicitly; the rest are caught by the readback.
- **Out-of-range and wrong-shape values throw rather than clamp**: "Value 150 out of range 0 to 100", "Value is not an array", "Array is not a number", "Value “NaN” of element 0 in the array is not a valid float". `hasMin`/`hasMax` predict the range exactly, per component on vectors (a Rect Size's `min 0`, a colour's ±3,921,568.6). Checked in the preflight so a multi-update call does not fail half-way.
- **`hidden` refuses even its own value back on this pass.** A 2D layer's Orientation threw "hidden" for `[0,0,0]`, the value it already held — writing back what is there is not a safe probe either (compare "Layers and transforms" above, measured with `setValue(p.value)` on an earlier pass). The preflight refuses `hidden` outright. A separated Position's leader is hidden (write `ADBE Position_0/1/2`), and its followers are hidden while it is not separated.
- **A layer style that is off refuses at runtime and nothing predicts it**: `dropShadow/mode2` says `canSetExpression: true` and throws "hidden". This is the case the rollback exists for, and the live regression uses it.
- **A keyed property throws on `setValue`** — "Can not call setValue() on a property with keyframes. Use setValueAtTime() or setValueAtKey() instead." — and keeps its keys. Time Remap is the clean example of both ends: off, it is `hidden`; on, it has two keys. The tool refuses rather than removing keys.
- **With an expression enabled, `setValue` changes the underlying value and leaves the expression alone.** `.value` then reads the evaluated result (`value / 2` over 60 reads 30) and `valueAtTime(t, true)` reads the 60 that was written, at every time on a property with no keys. A broken expression changes nothing about this. So the readback compares the pre-expression value, and the result reports `expressionEnabled` and the `evaluatedValue` that renders.
- **`NO_VALUE` and `CUSTOM_VALUE` throw on `setValue` exactly as on read** ("Can not get or set a value…", "…CUSTOM_VALUE has not been implemented"). Keylight's "About" is a `NO_VALUE` button; Curves' curve is `CUSTOM_VALUE`. There is no generic representation to write.
- **`LAYER_INDEX` and `MASK_INDEX` are 1-based indices with 0 for none**, range-checked by AE ("Value 99 out of range 0 to 5", "Value 5 out of range 0 to 1" with one mask), and a layer index that names a camera or light is refused ("The layer with that index is not an AVLayer"). Both report `canSetExpression: false` and `canVaryOverTime: false` and are writable.
- **`canSetExpression: false` is not "unwritable" where `canVaryOverTime` is false too**: shape Fill Rule and Composite, Keylight's View, a light's Casts Shadows all take values. Locked layers take values too — AE scripting ignores the lock.
- **A Shape read is a copy, and a write onto that copy keeps the mask's feather points** — the A1 rule, now for every Shape write. AE validates none of the feather arrays against the path: a feather point on a segment the path no longer has is kept as written, `featherSegLocs` must be integers ("…is not a valid int"), and empty arrays clear every point. A tangent list shorter than the vertex list is padded with zeros, not refused. All three are checked in the preflight.
- **Restoring a value with `setValue(previous)` round-trips exactly** — numbers, vectors, colours and a mask Shape with its feather points all read back identical. That is what makes the rollback reliable for what this tool accepts; it is still a sequence of writes, not a transaction, and a restore that fails is reported as such.
- **Two lookups of one property are never `===`**, whatever path spelled them. `propertyDepth`, `propertyIndex` and `parentProperty` answer on every node, so the index chain from the layer down (`5/11` for a shape layer's Opacity) is the identity duplicate updates are detected on.
- **Adding a property invalidates handles into its group** ("Object is invalid" on a Rect handle after a Fill was added beside it). `set_property_values` never adds properties, and still re-resolves each path before its write and its readback.

## Keyframe writes

Measured on **26.5x89**, 2026-10-11, in disposable comps at 23.976, 24, 25, 29.97, 30 and 59.94 fps, on 2D/3D shape layers, two-node cameras, spot lights, text with a position animator, a shape group (rect, fill, path), masks, two `ADBE Glo2`, Stroke, Set Matte and a precomp with Time Remap on (recipe 51). `set_keyframes` (`keywrite.jsx`) is built on these facts.

**Time**

- **`frame × comp.frameDuration` lands on the frame.** AE makes a 23.976 comp's `frameDuration` 0.04170837504171 — that is 1/23.976, not 1001/24000 (0.0417083333) — whether it was given 23.976 or 24000/1001, and `keyTime/frameDuration` reads back the integer to within 1e-13 for frames 0–1000 at every rate measured. `frameRate` is float32 (23.9759979248047) and is never the right divisor. `timeToCurrentFormat` agrees on every frame. Far into a long comp a frame key can be stored one key-time step off its frame (below) — frame 17981 at 30 fps is stored at 599.3666341 s, 1/30720 s early — and is still that frame's key.
- **Key times are comp seconds** even on a layer with a start offset or a 200% stretch: `setValueAtTime(20 frames)` lands at comp frame 20, and stretching the layer afterwards moves existing keys with it.
- **AE stores a key time on its own grid, not as given** (recipe 61; this replaces the earlier "AE keeps any time it is given"). It rounds the time to float32, then to the nearest step of a grid set by the comp's frame rate: 24576 steps/s at 12/24/48 fps, 25600 at 25/50/100, 30720 at 15/30/60/120, 32768 at 1, 20480 at 10, 35840 at 17.5, and 23976 at every NTSC rate (23.976, 29.97, 47.952, 59.94, 119.88 — given as decimals or 1001-rationals alike: a step of 1/23976 s, frameDuration/1000 at 23.976, /800 at 29.97, /400 at 59.94). Exact halves round up. The grid also follows the layer's **stretch** — at 137% the same request lands elsewhere — but **not** its start time. So 0.0123 s reads back 0.0123046875 at 30 fps, 10000 + 1/120 reads 10000.0087890625, and negative times and times past the end are accepted. The tool accepts 0 to `duration` inclusive and refuses the rest, naming the range in frames.
- **Two requests are one key exactly when AE stores them at one time** — within half a step. The earlier "2e-5 merged, 3e-5 did not" was a 23.976 fps measurement (a 4.17e-5 s step: 2e-5 is 0.49 of it); at 25, 30 and 60 fps 2e-5 s is two keys at every base time. No single formula covers every rate, and on a stretched layer far from 0 writing a key's own stored time can land a step away (30 fps, stretch 61%, 599.37 s) — so `set_keyframes` does not model it. It asks AE: a scratch comp with the target comp's `frameDuration`, holding a text layer with the target layer's start time and stretch, stores **bit-identical** times (144/144 across 23.976/25/30/60 fps, stretch 61–250%, times to 900 s). A request matches an existing key only when it is stored at that key's exact time there; two requests stored at one time are refused as one key; writes go at the requested time; replace keeps exactly the keys at the written stored times; readback and rollback compare stored times exactly; a rollback writes each key at a time the scratch layer confirms stores at its original time. The scratch comp is removed before the call returns, and the removal is confirmed by looking the item up again. If After Effects will not remove it, that is reported, never swallowed: the comp is named with its item id and `delete_project_item`, and the message says what happened to the animation — on success the result still reports the tracks applied and adds a `warning` (with `scratchCompLeftover: true`) saying not to re-send; on a refusal or failure the original error is kept whole and followed by whether the animation was untouched, rolled back or not fully restored. (Unit-tested only: a healthy After Effects does not refuse `remove()`.)
- **Not yet measured — recorded so it is not assumed.** The scratch-comp oracle was measured bit-identical with Opacity and Rotation on text layers and an effect parameter on solids. Time Remap (whose values are source seconds), mask paths, shape-layer paths, camera and light options, and text animator properties are assumed to round key times on the same layer time base, which is unmeasured. Separately, `set_effect_param` (C5.1, `effectstack.jsx`) still identifies a key with its own time rule — frameDuration/1024 or float32 spacing — which recipe 61 shows is exact only for the 25 and 30 frame-rate families; since it only confirms a key that demonstrably changed, its worst case at other rates is a refusal, not a false success. Moving it onto the same oracle is an open follow-up.
- **FIXED in B2.1 (2026-10-12): the fixed 1e-4 s match tolerance.** It was wider than the distance between two distinct keys (1/30720 s at 30 fps): a `merge` at 1.0000651 s silently overwrote the key at 1 s (90 → 70, `keysUpdated: 1`), and a `replace` to frames 0 and 30 kept the neighbouring key at 1.0000651 s, then refused and rolled back (verified by reading the keys back). Both now behave as AE stores the times: the merge adds a distinct key and leaves 90 at 1 s; the replace removes the neighbour. Reproduced and re-checked live (recipe 61).

**Metadata — every setter can change another field**

- **Fresh keys** from `setValueAtTime`/`setValuesAtTimes` are LINEAR/LINEAR, continuous and auto-Bezier off, label 0, and on spatial values zero tangents, spatial continuous on, spatial auto-Bezier off, roving off. **A key added beside an existing one copies that neighbour's interpolation** (a new key next to a HOLD key is HOLD), so "AE's default" depends on context; the tool sets every new key's metadata explicitly.
- **`setTemporalEaseAtKey` turns both sides Bezier and auto-Bezier off.** Setting the interpolation afterwards keeps the ease on Bezier sides: ease then `setInterpolationTypeAtKey(LINEAR, BEZIER)` keeps the out ease. AE remembers a Bezier ease under Linear: Bezier → Linear → Bezier brings it back.
- **`setTemporalContinuousAtKey(true)` turns both sides Bezier and copies the in speed onto the out side**; a later asymmetric ease is accepted and stays continuous. **`setTemporalAutoBezierAtKey(true)`** turns both sides Bezier, forces continuous and recomputes the ease; a later ease turns auto-Bezier off. **Setting Linear resets continuous.** Hence the per-key order: auto-Bezier → continuous → ease → interpolation, then spatial auto-Bezier → spatial continuous → tangents → label, with a readback of every key.
- **Ease arity**: 2 entries on TwoD (Rect Size), 3 on ThreeD (Scale, 2D or 3D layer), and **1 on everything else** — spatial Position, Orientation, OneD, COLOR and SHAPE. COLOR and SHAPE report `isSpatial: true`, yet every spatial call on them throws "does not have a spatial PropertyValueType". `KeyframeEase` refuses influence outside 0.1–100; speeds of ±1e7 are stored as given.
- **AE itself produces influence 0**: a first or last key a script switched from Linear to Bezier reads `{speed 0, influence 0}` on both sides, a distinct curve (values between the keys differ from influence 0.1). No setter can write it back, so a rollback that has to rebuild such a key reports itself INCOMPLETE rather than claiming success.
- **Inserting a key rescales its Bezier neighbours' influence** (41 → 35.4, 22 → 25.0) to keep the curve's shape, as the timeline does. A merge reports this as `neighbourEaseRescaled` and checks untouched keys on everything else.
- **Spatial**: `setSpatialTangentsAtKey` wants 3 numbers on ThreeD_SPATIAL even on a 2D layer, and turns spatial auto-Bezier off; spatial auto-Bezier on recomputes the tangents (float32: −33.3333320617676); spatial continuous accepts asymmetric tangents and stores them as given. **Tangents on Orientation rewrite the orientation value** ([90,0,0] read back [90,350,10]), so the tool refuses spatial options there.
- **Roving** is ignored on first and last keys; on a middle key it moves the key's time and zeroes its neighbours' influence. A roving track restored by setters came back with the roving key 0.15 s off, so the tool refuses any track with roving keys and never sets roving.
- **Labels** are 0–16 (17 throws). `setValueAtTime` on an existing key and `setValueAtKey` keep its interpolation, ease and label.

**Value types**

- **On a 2D layer, AE stores a fixed Z in every key, whatever it is given**: 0 on Position and Anchor Point (`[1,2,7]` reads back `[1,2,0]`), 100 on Scale. That differs from static writes, where the old Z is kept, and the tool refuses any other third number.
- **`canVaryOverTime: false` refuses every keyframe call** ("Can not perform any keyframe operations…"): every LAYER_INDEX and MASK_INDEX measured, and a shape Fill Rule. Hidden properties throw on `setValueAtTime` exactly as on `setValue`.
- **Source Text keys are HOLD-only** ("Invalid interpolation type for this property" on Linear) and need a rebuilt TextDocument, so they are refused, as in B1. **Markers** take `MarkerValue` keys with HOLD interpolation and stay with the marker tools.
- **Time Remap**: when on, it starts with two keys (0→0, end→end) and is range-checked 0 to source duration. **Removing its last key turns Time Remap off**, after which the property is hidden, so key sets are reconciled by writing first and removing second.
- **Expressions**: keys can be written under an enabled expression. `keyValue()` reads the key, `valueAtTime(t, false)` the evaluated result (`value * 2` over a key of 10 reads 20), and the expression is untouched.
- **Shapes**: a shape-layer path's keys may change vertex count (4 → 3, silent). A tangent list shorter than the vertex list is padded with zeros, so the tool refuses it, as in B1.
- **Mask paths: a key with a different vertex or feather-point count raises a MODAL warning.** Two keys written onto one mask with 1 and 0 feather points raised "After Effects warning: deleting points or feathers from an animated mask path deletes them from all keyframes for that shape unless you turn off the Preserve Constant Vertex and Feather Count option…". The dialog blocks ExtendScript, and so the whole bridge, until someone clicks OK: it stalled a live run for ten minutes on 2026-10-11, and AE minimized itself afterwards. With that preference on, AE also edits every other key. The tool requires every key of a mask path to keep the counts of the mask's existing keys (or of its static path when it has none), and refuses a mask whose existing keys already differ. Neither a write nor a rollback can then change a count, and the user's preference is never touched. Keys with equal counts (1 and 1) raise nothing.

**Cost** (2,000-key properties)

- Reads are cheap (~0.03 ms per key for everything). Some writes are linear in the property's length: `setValueAtTime` on an existing key 27 ms, `setValueAtKey` 5 ms, `removeKey` 4.4 ms, `nearestKeyIndex` 1.4 ms, and spatial auto-Bezier, roving and temporal auto-Bezier setters ~1.5 ms each. `setValuesAtTimes` writes 2,000 keys in 64 ms new or 160 ms over existing ones, keeping their metadata. So the tool makes one `setValuesAtTimes` call per track, computes key indices instead of looking them up, and calls a setter only where a key differs.
- **ExtendScript makes every retained object expensive**: pushing 5,000 small objects into an array took 3.8 s, while making and dropping them is free. The handler checks keys as it reads them instead of collecting them, and new keys with no metadata share one spec. Result: 10,000 new keys in 6 s in AE, the 546-key camera case in 0.12 s.
- **The bridge used to cost more than the handler.** ExtendScript's `JSON.parse` *is* native (`[compiled code]`; the `core.jsx` polyfill never runs) but superlinear, and far worse in a long-running session: 2.6 s for 38 KB and 14 s for 153 KB there, against 7 ms and 34 ms to evaluate the same text as a literal. End to end through `/op`, 546 keys took 2.8 s, 2,400 keys 16.5 s and 10,000 keys 34 s while the handler took 0.1–4 s. Requests now reach ExtendScript as a data literal and the bridge's share is 14–122 ms at those sizes — see "How a request reaches ExtendScript" in [fragile-areas-bridge.md](fragile-areas-bridge.md).

## Track mattes (AE 23+ API)

Measured on **26.5x89**, 2026-10-11, in disposable comps (recipe 47). The API is `layer.setTrackMatte(sourceLayer, TrackMatteType.X)`, `layer.removeTrackMatte()`, and three reads: `trackMatteLayer`, `hasTrackMatte`, `isTrackMatte`. `TrackMatteType` is exactly NO_TRACK_MATTE=5012, ALPHA=5013, ALPHA_INVERTED=5014, LUMA=5015, LUMA_INVERTED=5016.

- **The source is named, and nothing moves.** It may sit above *or below* the target; no layer is reordered by assigning, and moving the source afterwards keeps the link. One source can matte several targets, and a target can itself be another layer's matte. 2D/3D mixes, shape and text sources are all accepted.
- **AE turns the source's video off when it becomes a matte, and does not turn it back on.** Not on `removeTrackMatte()`, not when the target is re-pointed at another source. `set_layer` reports `sourceEnabled` rather than restoring it: whether the source should reappear is the caller's decision, and AE's own UI behaves the same way.
- **After `removeTrackMatte()`, `trackMatteType` keeps its old value** (it read `ALPHA` on a layer with no matte). `hasTrackMatte` / `trackMatteLayer` are the only truthful reads; `__trackMatteState` in `layers.jsx` reports `NO_TRACK_MATTE` whenever there is no source, and `get_layer_full` reads it the same way.
- **A `null` source is accepted and does nothing** — no throw, no change. That is why the source is always resolved and checked in JSX before the call. AE does refuse, with an error: `NO_TRACK_MATTE` as the type ("Invalid parameters"), the layer itself, a layer from another comp, a camera or a light ("not of the correct type"), an undefined or non-enum type, and the arguments in the wrong order.
- **Deleting a matte source clears its targets' mattes without a word** (`hasTrackMatte` reads false afterwards; recipe 54). A duplicated *target* keeps the same source; a duplicated *source* is a matte for nothing. A camera or light has no `setTrackMatte` at all (`undefined`, not a throw), and AE accepts `setTrackMatte` on a **locked** target — `set_track_matte` refuses that for consistency with every other structural write on a locked layer.
- **The old `trackMatteType = X` assignment still works, and silently uses the layer directly above.** That is what `set_layer` did for every call while accepting a `trackMatte.layerId` it never read. It now always calls `setTrackMatte` with an explicit source; omitting `layerId` resolves the layer above in the handler and is refused on the top layer.

## Layer structure

Measured on **26.5x89**, 2026-10-11, in disposable comps (recipes 54 and 55). These are why `structure.jsx`, `duplicate_layer` and the parenting helpers in `layers.jsx` are shaped the way they are.

- **`layer.id` is stable through reorder, parenting, duplication (the copy gets a new id) and `precompose` with `moveAllAttributes:false`. It is NOT stable through `precompose` with `moveAllAttributes:true`.** There every moved layer is recreated inside the new comp with a new id, the old `Layer` objects read "Object is invalid", and the replacement precomp layer in the outer comp is new as well. `precompose_layers` reports the mapping (`innerLayers[].fromLayerId`, matched by stacking order and confirmed by name) and `layerIdsChanged`.
- **Reorder.** `moveBefore`/`moveAfter` take a layer; `moveToBeginning`/`moveToEnd` take nothing. AE refuses a layer moved relative to itself ("Can not move a layer before or after itself") and any move of a **locked** layer ("...because the Layer is locked"). Moving another layer relative to a locked one is allowed. A shy or guide layer moves like any other. `move_layer` checks the landing against the destination the caller named (the id now below or above it, or index 1 / numLayers), not against an index it computed.
- **Duplicate.** `layer.duplicate()` puts the copy directly **above** the original — not at index 1 — with a fresh id, AE's own `"<name> 2"` name, the same parent, the same matte source and the **same source item** (no footage, solid or comp is added to the project). A locked layer duplicates into a locked copy, and a locked layer's `name` cannot be set, so `duplicate_layer` refuses `newName` on a locked layer up front.
- **Parenting.** A plain `layer.parent = p` **compensates**: the world pose is kept and the local values change (2D: `[100,100]` under a parent at `[500,300]` read back `[-400,-200]`; 3D: position and orientation both rewritten). `layer.setParentWithJump(p)` exists and keeps the local values exactly — the layer visibly jumps — in 2D and 3D, and `setParentWithJump(null)` unparents the same way. So `parent_layer`'s old `preserveTransform:false`, which did `layer.parent =`, was a compensated assignment in all but name; it now jumps. The compensating assignment still goes wrong when the new parent was itself re-parented earlier in the same evaluation (issue #28 reproduced: a child of a 200%-scaled grandparent landed at the unscaled offset), which is why `preserveWorldTransform:true` keeps the checked-and-corrected path (2D only; see "Parenting that does not move the layer" in `layers.jsx`).
- **Shape and text layers are not `instanceof AVLayer` in ExtendScript** (measured on 26.5x89, recipe 67: false for both, true for a null and a solid, false for a camera, whose `threeDLayer` reads undefined), though Adobe documents both as AVLayer subclasses. `__ptChain` (`layers.jsx`) used `!(l instanceof AVLayer)` to mean "a camera or light", so the check-and-correct path for issue #28 never ran for the two most common layer types, and the note named the shape layer itself as *"a camera or light in the chain"* (recipe 62). Fixed (2026-10-12): cameras and lights are now named positively by `instanceof CameraLayer` / `LightLayer`, and the note says which one; the 3D refusal is unchanged. Live (recipe 67), shape and text children of a 60%/30° shape parent, a text layer mid-chain, a shape under a 150%/−20° null and the way back out all came back checked with no notes and the world placement held, read independently with `sourcePointToComp`; AE's own compensation was right every time, so the correction's *write* path for these kinds is proven by `tests/unit/parent-transform.mjs` only. Other `instanceof AVLayer` tests remain: `comps.jsx` and `footage.jsx` use it to skip source-less layers (shape and text have no source, so harmless), but `propwrite.jsx`'s `LAYER_INDEX` check would refuse a shape or text layer as an effect's layer parameter — unmeasured, not changed here.
- **Parenting rules.** AE refuses a self-parent and a parent that is a descendant with one message ("cannot be itself nor one of its children"); `__planParent` walks the proposed parent's chain first and names the cycle. A locked layer's `parent` cannot be set; a locked layer **can** be a parent. Every pairing of 2D, 3D, null, camera and light is accepted — a camera under a 2D null, a 2D null under a camera, a light under a camera, 2D under 3D and 3D under 2D — so there is no compatibility rule to enforce.
- **`precompose(indices, name, moveAll)` returns the new `CompItem`.** It files it in the **outer comp's folder** (the root only when the outer comp is there), sizes it like the outer comp (moveAll:true) or like the layer's source (moveAll:false: a 200x200 solid made a 200x200 comp, 5.5 s for a layer ending at 5.5), and puts the replacement layer at the **index of the topmost selected layer**, even for a non-contiguous selection. The selection afterwards is the replacement layer; the viewer does not change. AE accepts a duplicated index (`[1,1]`) and an empty name; it refuses an empty array or an index out of range, `moveAll:false` with more than one layer, `moveAll:false` on a camera or light, and `moveAll:false` on a text or shape layer ("layer does not have a source").
- **What moveAll:true does inside.** Effects, masks, keyframes, in/out points, 3D, locked, shy and guide flags all travel with the layer, and the selection's stacking order is kept. Parenting and mattes between two selected layers are kept (re-pointed at the new ids).
- **What moveAll:false does.** The layer keeps its id, effects, masks, keyframes, timing, parent, its children, its own matte and its role as another layer's matte source; only its source becomes the new comp, which holds one plain copy of the original source, centred. The layer is **renamed to the new comp's name**, and AE rewrites other layers' `thisComp.layer("Old name")` expressions to the new name.
- **What moveAll:true does across the selection boundary — silently, every case measured:**
  - a selected child of an unselected parent loses the parent, and AE bakes the parent's transform into the child's values (`[0,0]` keys under a parent at `[400,300]` read `[400,300]` inside);
  - an unselected child of a selected parent is re-parented to the new precomp layer, whose transform does not carry the parent's motion;
  - a selected matte target whose source stays outside gets a **copy** of the source inside the precomp, and the original source is left behind, disabled and matting nothing;
  - a selected matte source whose target stays outside: the target's matte is re-pointed at the precomp layer;
  - an outside expression naming a moved layer breaks (AE disables it: "layer named 'E' is missing"); one using `thisComp.layer(n)` keeps evaluating against whatever is at index `n` now — the replacement layer — with no error at all; a moved layer's expression naming an outside layer has nothing to find inside;
  - a camera or light moves out of the comp it was lighting; a 3D layer's replacement is 2D and not collapsed; an adjustment layer stops adjusting the unselected layers that were below it.

  `precompose_layers` refuses all of these before anything changes — the rule is "select both ends of a relationship, or break it first". It also refuses a `layer(<computed>)` reference and `index`/`numLayers` in an expression on a layer whose index or comp changes, because neither can be checked without evaluating it, and an effect layer-parameter (`PropertyValueType.LAYER_INDEX`) naming a layer across the boundary — that last one conservatively, not measured. **Not detected:** expressions in *other* comps that reach in with `comp("Outer").layer(...)`, and any reference built from strings at run time. `moveAll:false` skips the boundary checks: the layer keeps its id, so its relationships hold, and AE rewrites name references itself.
- **Undo is unmeasured for precompose.** Each call is one undo group through `dispatch`, but a script cannot invoke Undo over this bridge; whether one Cmd-Z restores a precompose exactly — the moved layers back with their original ids — has to be checked by hand.

## Layer timing and Time Remap

Measured on **26.5x89**, 2026-10-11, in disposable comps with a generated 4 s 30 fps clip, a 3 s WAV, a PNG still, a 3 s precomp, text, shape, solid, null, camera and light (recipe 56). These are why `timing.jsx` is shaped the way it is.

- **startTime, the trims and stretch are three different operations.** `startTime` slides the whole layer: inPoint, outPoint and every keyframe — Time Remap's too — move by the same amount. `inPoint`/`outPoint` are trims: they move no keyframes and do not retime the source. `stretch` retimes playback: it scales inPoint, outPoint and every key about `startTime` (start 1, in 2, out 4 at 100 → in 3, out 7 at 200; Time Remap key times scale, their values do not) and leaves `startTime` where it is. Changing which source frame plays when is Time Remap's job, never these.
- **Setting `inPoint` drags `outPoint` by the same amount**, on every layer type (a solid in 0/out 5 → in 2 gives out 7). Setting `outPoint` alone moves nothing else, and AE accepts an outPoint **at or before** the inPoint (a solid read in 6, out 1) — a layer with no frames, no error. So `set_layer_timing` writes stretch, startTime, inPoint and then outPoint explicitly, after checking out > in on the final values.
- **A footage, audio or precomp layer without Time Remap is clamped to its source — silently.** inPoint and outPoint land inside `[startTime, startTime + sourceDuration × stretch/100]` whatever is asked: outPoint 8 on a 4 s clip reads 4, inPoint −2 reads 0, and the bounds follow startTime and stretch (start 1 at 200%: [1, 9]). An inPoint drag past the source end is clamped the same way. With Time Remap on there is no bound (outPoint 8, 15 land). Stills, solids, nulls, text, shapes, cameras and lights are unbounded either way — a negative inPoint and an outPoint past the comp end both land. `set_layer_timing` refuses a trim outside the bound and names the range.
- **stretch is −9900..9900 and stored as a float32 factor.** Past ±9900 AE throws "out of range -9900 to 9900"; anything with a magnitude under 1 (0, 0.001, 0.5, 0.999) is stored as ±0.999451 with no error. 120 reads back 120.000004768372 (`Math.fround(1.2) × 100`), so a stretch readback needs a relative tolerance — a 1e-6 absolute one rejected a write that had landed, and the rollback ran.
- **Negative stretch reverses the layer and mirrors its times with a 1/100-frame offset.** At −100 a 4 s clip starting at 0 reads in −0.000333, out −4.000333 — inPoint > outPoint, entirely before the comp starts — and every key (Time Remap's too) mirrors about startTime with the same offset. Going back to +100 restores the exact original times. `set_layer_timing` writes no negative stretch and, on a reversed layer, only a positive stretch on its own; reversal belongs to Time Remap.
- **Times are quantized slightly.** startTime 0.0123 reads 0.012305, outPoint 2.98765 reads 2.987663. Frame multiples of `comp.frameDuration` read back to 1e-15 — at 23.976, frames 0, 1, 12, 99, 150 and 240 for start, in and out all read back as whole frames. A 23.976 comp made with `addComp(..., 23.976)` reports frameDuration 0.04170837504171 (1/23.976, not 1001/24000), so frames convert with the comp's own `frameDuration`, never a nominal rate.
- **Every timing write and `timeRemapEnabled` on a locked layer throws** ("Can not set attribute “inPoint” on Layer … because the Layer is locked"). The tools refuse first, as the C3 structure tools do; `set_layer` can unlock and retime in one call.
- **Time Remap exists only on footage (video and audio) and precomp layers.** `canSetTimeRemapEnabled` is true for those and false for stills, solids, nulls, text and shapes, which throw "Can not set timeRemapEnabled … Check layer.canSetTimeRemapEnabled". A camera or light has neither property: `cam.timeRemapEnabled = true` "succeeds" by creating a plain script property, and nothing in AE changes. Gate on `canSetTimeRemapEnabled === true`, never on the assignment not throwing.
- **Enabling creates exactly two LINEAR keys: `(startTime, 0)` and `(startTime + sourceDuration × stretch/100, sourceDuration)`**, whatever the trims — start 1 gives keys at 1 and 5; 200% at 0 and 8; 50% at 0 and 2; trimmed in 1.5 at 0 and 4. Neither key is continuous or auto-Bezier and both are unlabelled. The formula keeps holding as startTime and stretch move the keys later, which is what lets "still default" be decided: two keys exactly there with those values, linear both sides, no flags, no label, and no expression text. Two keys is not proof of default — a moved key or a changed value is custom.
- **Enabling can move the out point.** On a layer trimmed in to 1.5 by a raw `inPoint` write, with the out point clamped at the source end, enabling moved the out point to 5.5 (in + 4); after an explicit outPoint write it did not move. `set_time_remap` puts back any trim AE moved and reports both values.
- **Disabling deletes every Time Remap key and re-clamps the trim.** Re-enabling recreates only the two defaults — custom keys are gone. An out point extended to 8 with Time Remap on reads 4 again after disabling. **The expression is not deleted**: its text stays on the hidden property (`expressionEnabled` still true) and is live again the moment Time Remap is re-enabled. So `set_time_remap` refuses to disable a customized Time Remap (keys or expression) unless `discardTimeRemap:true`, and reports a revived expression on enable.
- **There is no `reset_time_remap`.** Disabling with `discardTimeRemap:true` and enabling again gives AE's two default keys back — except that a stored expression comes back with them, so a reset is those two calls plus `clear_expression`. A dedicated op would have to hide that.
- **Timing changes stay local.** A layer's parent, its matte source, and a precomp layer's source comp (id and duration) are unchanged by startTime, trims and stretch on any of them; `layer.id` never changes.
- **Undo is unmeasured** for timing and Time Remap. Each call is one undo group; a script cannot invoke Undo over this bridge.

## Effect stack

Measured on **26.5x89**, 2026-10-11/12, in disposable comps (recipe 57): Gaussian Blur, three Glows, Curves, Tint, Fill, Transform, Keylight 906, Displacement Map, Slider Control, on solids, nulls, text, shapes, precomps, adjustment layers, cameras and lights. These are why `effectstack.jsx` is shaped the way it is.

- **An effect has no id.** `effect.id` and `effect.uniqueId` are undefined. `propertyIndex` is its position; `matchName` names its type and repeats across copies; the display name is mutable. So every structural tool takes a locator — `{effectIndex, matchName, effectName, fingerprint}` from `get_effect_stack` — checks it against the live stack, and refuses a stale one with the current stack in the message rather than re-resolving it. **Index + matchName + name is not enough**: two effects can share all three (two "Bloom"s), and after the live proof swapped them the first one's old locator matched the other. The `fingerprint` — FNV-1a over every readable value, key and expression, the enabled state and nested groups — is what refused it. It leaves out the *current* value of a keyed or expression-driven parameter (the keys and the text stand for it), so it held across a playhead move from 0 to 0.5 s; any edit changes it. Two effects identical in everything a script can read cannot be told apart at all — and acting on either gives the same stack.
- **Every held reference into a stack goes invalid after any structural change.** After `moveTo`, `duplicate()` or `remove()`, every effect object taken before it — the one that was moved or duplicated included — throws "Object is invalid". The Effects group itself stays usable. The tools re-fetch by index after each write and never keep a handle across one.
- **AE names effects itself, and only when it creates them.** A second Glow is added as "Glow 2", a third as "Glow 3". A copy is named after its source's base with the next free number above the highest in use: duplicating "Glow 2" beside Glow/Glow 2/Glow 3 gives "Glow 4", "Glow 7" gives "Glow 8", a renamed "Bloom" gives "Bloom 2". Adding uses the plain display name whenever it is free ("Glow" again once no effect is called that). **A rename to a name already in use is accepted** — two effects called "Bloom" — and `property("Bloom")` / `property("ADBE Glo2")` return the first match. Hence `occurrence` and `sameMatchNameCount` in every record, and paths by index once a matchName repeats (the same rule `inspect_property_tree` uses).
- **`duplicate()` puts the copy directly below its source**, and copies the enabled state (a disabled Glow's copy is disabled), every value, keyframes with their interpolation (a HOLD key stays HOLD), expressions (still enabled), the Compositing Options' Effect Opacity, and layer-reference parameters. `duplicate_effect` verifies all of that by fingerprint against the source and removes a copy that does not match.
- **`moveTo(n)` leaves the effect at final index n.** `moveTo(its own index)` is accepted and changes nothing; 0 or past the end throws "Can not move this property to index 99 because parent property has only 9 child properties."
- **Removing one of several identical effects removes exactly the one addressed** — and every reference to any effect on that stack goes invalid, as above.
- **Layer-reference parameters follow the layer, not the index.** Displacement Map's layer parameter (`LAYER_INDEX`) on the original and on its duplicate both read 2 while the source layer was at index 2, and both read 1 after it moved to the top.
- **Cameras and lights have no Effects.** `property("ADBE Effect Parade")` is `null` on them; solids, nulls, text, shapes, footage, precomps and adjustment layers all take effects (`canAddProperty` true, `addProperty` lands). A bad matchName: `canAddProperty` is false and `addProperty` throws "Can not add a property with name … to this PropertyGroup". A display name ("Gaussian Blur") is accepted by `addProperty` and creates the matchName ("ADBE Gaussian Blur 2").
- **A locked layer does not stop a script.** On a locked solid, `addProperty`, `duplicate()`, `moveTo`, a rename, `enabled = false`, `setValue` on a parameter and `remove()` all landed. So the lock policy is ours, and it differs by kind of tool. **The dedicated effect tools refuse a locked layer and take a locator:** `add_effect`, `remove_effect`, `duplicate_effect`, `move_effect` (C5) and, since C5.1, `set_effect_param` and `set_effect_enabled` (both through `__esTarget` → `__esRequireUnlocked`), as the C3/C4 structure and timing tools do. **The generic property-path writes check neither:** `set_property_values` (B1) and `set_keyframes` (B2) write a locked layer, *including an effect parameter reached by its path*, and an index segment in that path names whatever effect sits there now. That is a gap in the generic tools, not in the C5.1 ones — and the supervised trial (recipe 62) went through it: its effect write used `set_property_values` because the client's cached tool schema could not send `set_effect_param`'s locator, so that write was checked by neither the lock nor a locator (the layer happened to be unlocked).
- **Removing an effect an expression names breaks that expression with no error anywhere else.** A Blurriness expression `effect("Drive")("Slider")` read 7; after the "Drive" Slider was removed (a duplicate "Drive 2" remained) it read 25 — the static value — with `expressionError` "Expression disabled … effect named 'Drive' is missing or does not exist". An index reference (`effect(2)`) does not error at all when indices shift; it reads another effect. So remove/duplicate/move scan every expression in the comp for `effect()` calls that could address this stack, refuse on a name match (remove) or an index the change shifts, and afterwards compare `expressionError` before and after.
- **That scanner contains no regular expression.** The first version matched `effect(...)` calls with one RegExp (an optional `layer(…).` / `name.` prefix ahead of lazy `[^()]*?` groups). V8 runs it instantly. ExtendScript never returned from a single `exec()` of it: twice it froze After Effects until it was force-quit, the second time inside a loop capped at 20 iterations that never got a turn — the hang is inside one `exec`, not a `lastIndex` that fails to advance. The replacement is `indexOf`/`charAt` only, every loop moving strictly forward or strictly toward 0; live it scans 20,000 back-to-back `effect` (120 KB) in about 40 ms and the rest of the adversarial corpus in single milliseconds, identically on a second pass. `tests/unit/effect-stack.mjs` fails if a regex comes back into it.
- **CUSTOM_VALUE parameters cannot be read or written from a script.** Curves' curve ("ADBE CurvesCustom-0001") throws "This propertyValueType CUSTOM_VALUE has not been implemented" on `.value`. `duplicate()` copies it (it is AE's own copy), but no script can verify that, so `duplicate_effect` reports it as `notComparable`. **There is no effect-level copy API** (`copyToComp` exists on layers, not on effects), and a copy rebuilt parameter by parameter on another layer would silently lose exactly this data — which is why there is no `copy_effect`.
- **A key time is rounded to the nearest frameDuration/1024, or to float32 spacing where that is coarser** — true of the 25 and 30 frame-rate families; recipe 61 has every rate (60 fps steps at frameDuration/512, NTSC at frameDuration/1000 or finer) and the layer's stretch. `set_effect_param` uses this only to confirm a key that demonstrably changed, so at another rate its worst case is a refusal, not a false success; `set_keyframes` asks After Effects instead (Keyframe writes, above). Measured in a 30 fps comp: the grid is 1/30720 s — at 1 s, offsets of 0.25, 0.40 and 0.49 of a step land *on* the key at 1 s, 0.51 to 1.4 make a distinct key one step later, 1.6 and 2 two steps later; 0.0123 → 0.0123046875; 1/120 offsets exact; at 1000 s off by 3.3e-5; at 5000 s distinct keys no closer than 2^-11 s; at 10000 s, 10000 + 1/120 is stored as 10000.0087890625 (0.00046 s off) and 10000 + 1e-5 lands *on* the key at 10000. So `set_effect_param` identifies the key a write made by diffing the key list before and after by stored time (exact), uses one storage step *at that time* only to confirm that a key which demonstrably changed is the one asked for, and requires every other key and the expression to be unchanged. When *no* key changed, the write counts as a no-op only on a key whose stored time is exactly the requested time: one step is also the closest two distinct keys can be, so a dropped write one step from an unchanged key holding the same value would otherwise pass (reproduced by Codex at 1 s; refused since). A relative tolerance (1e-6 × t, 0.01 s at 10000) once took a key 1/120 s away for the one written and reported a dropped write as a success.
- **Undo is unmeasured** for the effect-stack writes. Each call is one undo group; a script cannot invoke Undo over this bridge.

## The render queue

- **`OutputModule.setSettings` rejects Format, Channels, Depth and Color as read-only**, although `getSettings(GetSettingsFormat.SPEC)` lists all four — SPEC is the domain, `STRING_SETTABLE` is the writable list (issue #95, measured on 26.3 from four starting states). There is nothing to fix in code because the render queue is out of scope, but it is why any future render op must apply an output-module template by name rather than set a codec, and read `getSettings(STRING)` back before trusting it.

## Writing files from ExtendScript

- **`set_house_style` writes through ExtendScript's `File`, whose macOS default `lineFeed` is `"Macintosh"` — every `\n` became a bare `\r` on disk.** The round trip hid it (`File.read` normalises line endings), the unit tests never touch a real `File`, and the only symptom was a designer's editor showing the guide as one line. `style.jsx` sets `file.lineFeed = "Unix"` before opening for write; anything else in `packages/jsx/` that ever writes a text file must do the same, since nothing offline can catch it — recipe 10 reads the bytes.
